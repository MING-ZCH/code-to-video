# Code-to-Video

Every frame is a pure function of time `t`, painted by code you write. Nothing is generated by a model at render time; the output is reproducible, auditable and editable shot by shot.

## Locate the kit

The repository (default `~/Desktop/code-to-video`) contains `ANIMATION_GUIDE.md` (the rules and full API — read it before drawing anything), `engine/` (shared, read-only), `projects/<name>/` (one per input), `render.mjs` and the CLI `bin/c2v.mjs`. If it isn't there, ask where it is. Run `npm install` once.

Every command below is `node bin/c2v.mjs <cmd> <name>`. The same tools are available over MCP (`mcp/c2v-mcp.mjs`: c2v_new, c2v_check, c2v_reads, c2v_cost, c2v_sheet and c2v_strip (these two return images), c2v_selftest, c2v_render, c2v_guide). Prefer the MCP tools when they're connected: sheets come back as images you can look at directly. On a Linux box without a GPU use `scripts/vm-c2v.sh` instead (software WebGL); it is slow (seconds per watercolour frame), so do look-checks with `--medium=flat` and/or `--scale=0.5` and leave final renders to a machine with a GPU.

## The loop

| step | skill | command | output |
|---|---|---|---|
| 1 ingest | (this file) | `c2v new <name> --from=<input>` | `projects/<name>/input/brief.md`: timed lines / story beats / palette / tempo / source shots |
| 2 storyboard | **c2v-storyboard** | edit `STORYBOARD.md` | logline, world, motif, arc, shots with EVENT + reads + transitions |
| 3 build | **c2v-build** | edit `scenes/*.js`, `c2v check`, `c2v reads` | shots that pass check with 0 errors; every reads warning fixed or explained |
| 4 look | **c2v-review** | `c2v review <name> --medium=flat`, then brush sheets/crops | `out/review/*.jpg` + filled `REVIEW.md`; iterate until it reads |
| 5 deliver | **c2v-deliver** | `c2v selftest`, `c2v render`, `c2v report` | `out/video.mp4`, `out/report.html`, metrics |

Pieces over ~30 s: plan chapters and split the build across agents with **c2v-orchestrate**.

## Non-negotiables

- No video/image generation models anywhere. Inputs are parsed and measured (`c2v ingest`); everything on screen is drawn by code.
- Frames are pure functions of `t`: no `Math.random()`, no wall clock, no state carried between frames. `c2v check` errors on these; `c2v selftest` proves it.
- Storyboard before code. Show the storyboard to the person and let them react before building, when there is a person in the loop.
- Look at your frames. You can't judge motion or timing from code. Every shot gets a sheet, every key motion and seam a strip, every story-carrying face a crop.
- Report honestly: say which checks ran where (GPU vs software render), what you looked at, and what is still unverified.

## Inputs → what to do with them

| input | brief gives you | storyboard approach |
|---|---|---|
| lyrics (`.lrc`, `.srt`, timestamped `.txt`) | timed lines | one visual idea per line; act it, don't write it; cut on bar lines |
| song (`.mp3`, `.wav`) | duration, BPM, first beat, loudness sections | sections → chapters; hits on beats (`PROJECT.bpm/offset` are prefilled) |
| script (`.md`, `.txt`) | story beats with read-time estimates | beats → shots; merge or split until every shot has one EVENT |
| image (meme, key art) | size, palette, reference thumbnail | the image is a moment: build the shots before and after it; reuse its palette; restyle it per segment with `stylize()` for multi-style remixes |
| video clip | cuts, keyframe sheet, music analysis | adapt the beats and timing, never trace frames; keep the rhythm, redesign the pictures |

If the music analysis says `confidence: low`, set `bpm`/`offset` by hand (tap along, or read them from the score); on short excerpts check the first-beat phase on a strip.
